# Arquitectura del Sistema (Modelo C4)

Esta página resume cómo está construido **Aliento Andino** usando el [modelo C4](https://c4model.com) de Simon Brown: cuatro niveles de zoom, de lo general a lo particular. Sirve para entender qué piezas intervienen cuando practicas Quena, Zampoña o Tarka y quién se encarga de cada tarea.

:::info Diagramas completos
Los diagramas Mermaid originales viven en el repositorio: consulta el [modelo C4 completo en GitHub](https://github.com/moises-cisneros/aliento-andino/blob/main/docs/C4_MODEL.md). Aquí se presentan los mismos niveles en formato de tablas y listas.
:::

## Principio rector: inferencia 100% local

El análisis de tu afinación (pitch) y de tu postura ocurre **dentro de tu teléfono**. El audio y el video crudos nunca se envían a servicios de nube; solo se sincronizan resultados compactos (puntajes y telemetría JSON de menos de 5 KB).

## Nivel 1: Contexto del sistema

Ubica a la plataforma dentro de su entorno: quiénes la usan y con qué sistemas externos se relaciona.

| Elemento                        | Tipo                | Qué hace                                                                                  |
| :------------------------------ | :------------------ | :---------------------------------------------------------------------------------------- |
| **Estudiante de viento andino** | Persona             | Practica Quena, Zampoña o Tarka con la app móvil y recibe retroalimentación en vivo.      |
| **Docente / Administrador**     | Persona             | Usa el panel web para gestionar lecciones, digitaciones y moderar la comunidad.           |
| **Plataforma Aliento Andino**   | Sistema de software | Procesa la práctica, autentica usuarios, guarda el progreso y ofrece tutoría interactiva. |
| **Firebase Cloud Messaging**    | Sistema externo     | Envía notificaciones push de racha diaria y recordatorios.                                |
| **GitHub Pages**                | Sistema externo     | Aloja este manual de usuario.                                                             |
| **Almacenamiento de objetos**   | Sistema externo     | Guarda los respaldos cifrados diarios de la base de datos.                                |

## Nivel 2: Contenedores

Las aplicaciones y almacenes que componen la plataforma.

| Contenedor           | Tecnología                        | Responsabilidad                                                                                 |
| :------------------- | :-------------------------------- | :---------------------------------------------------------------------------------------------- |
| **App móvil**        | Flutter 3.x (Dart)                | Práctica, captura de audio y cámara, feedback y sincronización offline.                         |
| **Motor on-device**  | C++ (YIN / SPICE), MediaPipe, SLM | Detecta la nota que tocas en menos de 50 ms, evalúa tu postura y redacta consejos sin conexión. |
| **Panel web**        | Angular 21 (Standalone)           | Gestión de lecciones y digitaciones, analítica y moderación.                                    |
| **Reverse proxy**    | Nginx                             | Punto de entrada: SSL, límites de uso y enrutamiento hacia la API.                              |
| **API backend**      | FastAPI (Python 3.12)             | Autenticación, lecciones, rachas, rankings y muro social.                                       |
| **Microservicio ML** | FastAPI (puerto 8001)             | Preguntas frecuentes semánticas y validaciones armónicas complejas.                             |
| **Base de datos**    | PostgreSQL 16                     | Usuarios, lecciones, sesiones de práctica y relaciones sociales.                                |
| **Portal de docs**   | Docusaurus 3                      | Este manual de usuario.                                                                         |

Flujo principal: la app móvil y el panel web hablan con el reverse proxy por HTTPS; el proxy reenvía al backend (puerto 8000) o al microservicio ML (puerto 8001); el backend guarda todo en PostgreSQL.

## Nivel 3: Componentes

### Backend

El backend respeta capas estrictas: **routers (HTTP) → servicios (lógica de negocio) → modelos (base de datos)**. Los routers nunca contienen lógica de negocio ni consultas SQL.

| Área           | Responsabilidad principal                           |
| :------------- | :-------------------------------------------------- |
| Autenticación  | Registro, inicio de sesión y rotación de tokens.    |
| Lecciones      | Catálogo, secuencias de notas y digitaciones.       |
| Práctica       | Registro de sesiones, cálculo de XP e historial.    |
| Social         | Publicaciones, comentarios, reacciones y reportes.  |
| Rankings       | Tabla de posiciones, rachas y logros.               |
| Analítica      | Métricas por instrumento y deserción para docentes. |
| Notificaciones | Recordatorios y alertas push.                       |
| Tutor          | Consejos de respaldo y registro de uso de IA.       |
| Auditoría      | Bitácora de acciones administrativas.               |

### Panel web

Organizado en tres capas: **vistas** (lista y editor de lecciones, catálogo de digitaciones, moderación, analítica, auditoría) que consumen **servicios de dominio** basados en Signals, apoyados por una capa **core** con guardas de acceso por rol y un interceptor que inyecta el token de sesión.

### App móvil

Organizada con Clean Architecture y BLoC, en cuatro capas:

1. **Presentación**: afinador, práctica, digitación interactiva, cámara de postura, lecciones sin conexión, perfil y muro social.
2. **Estado (BLoC)**: instrumento activo, afinador, práctica, postura, descargas, perfil, social y autenticación.
3. **Motores on-device**: detector de pitch YIN, calibrador de soplo, pipeline MediaPipe, notificaciones locales y orquestador del tutor SLM.
4. **Datos**: repositorios que combinan la API REST con una base local Drift/SQLite para trabajar sin conexión.

## Nivel 4: Código y datos

El nivel de detalle más fino describe el modelo de datos y las clases del dominio.

- **Entidades principales**: usuarios, categorías, lecciones, secuencias de notas, digitaciones, sesiones de práctica, publicaciones, comentarios, reacciones, seguidores, reportes, logros, notificaciones y bitácoras de auditoría.
- **Instrumentos soportados**: `quena`, `zampona` y `tarka`.
- **Niveles de dificultad**: principiante, intermedio y avanzado.
- **Relaciones clave**: una lección contiene muchas notas y puede practicarse muchas veces; cada sesión de práctica puede compartirse como publicación; cada usuario acumula XP, racha y logros.

El diagrama entidad-relación completo y el diagrama de clases están en el [modelo C4 del repositorio](https://github.com/moises-cisneros/aliento-andino/blob/main/docs/C4_MODEL.md).

## Resiliencia y manejo de errores

| Situación                        | Qué ocurre                                                                                  |
| :------------------------------- | :------------------------------------------------------------------------------------------ |
| Datos inválidos                  | El sistema responde con un error descriptivo (HTTP 422) indicando qué campo corregir.       |
| Micrófono o cámara con problemas | El motor on-device reintenta y avisa sin interrumpir el sonido; nunca inventa notas falsas. |
| Sin conexión                     | Tu práctica se guarda en el dispositivo y se sincroniza después con reintentos seguros.     |
| Falla del servidor               | La transacción se revierte y se registra el error; se muestra la causa real.                |

Reintentar el envío de una sesión **no duplica** tu XP ni tus estadísticas: cada sesión lleva un identificador único (`client_id`) que la base de datos valida.
